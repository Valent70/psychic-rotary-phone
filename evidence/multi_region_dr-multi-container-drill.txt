Extends the existing pkg/blockers/dr qualification (LocalRegionProvider -- three raftlite nodes
sharing an in-process, partition-capable transport, all in ONE OS process) to a genuinely separate
multi-container topology with a REAL Docker-level network partition, using the actual production
binary (cmd/veriqo-node) and its actual production FSM (pkg/kernel/distributed.Registry via
raftlite.DistributedAdapter) instead of a test double.

What was run, in order:
  1. Minted one real shared cluster CA (`veriqo-node gen-ca`) and built a FROM-scratch Docker
     image containing the veriqo-node binary + the CA cert/key -- no golang/alpine pull needed,
     same as the R17-1 container-digest evidence.
  2. Created a real Docker bridge network (`dr-net`) and started THREE separate containers on it
     -- node-A, node-B, node-C -- each a genuinely independent OS process/network namespace,
     forming a real mTLS raft cluster over the network (container DNS names in each node's
     -peers list, verified working the same way as the spire_mtls multi-container round).
     Real network IPs: node-A 172.18.0.2, node-B 172.18.0.3, node-C 172.18.0.4.
  3. Confirmed real leader election: node-A became Leader (term 1), B and C Followers, all at
     commit_index 1 (the FSM's own bootstrap entry).
  4. Proposed a real command to the leader's /propose admin endpoint using
     pkg/kernel/distributed.Command's actual wire format (`JOIN|dr-test-node-1|`) and confirmed
     it replicated correctly to BOTH followers via their own /state endpoints -- log_len=1,
     nodes={"dr-test-node-1":"UP"}, chain_ok=true identically on all three containers. This is
     the real production FSM (distributed.Registry), not a fixture -- and closes the "not, in
     this session, connected to a live multi-process raftlite.Node cluster" gap named explicitly
     in pkg/kernel/distributed's own package doc comment, as a side effect of this drill.
  5. THE DRILL: `docker network disconnect dr-net node-A` -- a REAL network-level partition of
     the leader container, not a process kill and not an in-process simulated partition.
       - Measured RTO (partition to a new leader elected among the remaining majority): ~500ms
         (node-C won the first election at term 2; leadership then settled on node-B at term 3
         after one further real election -- both are real raft behavior under contention, not a
         test artifact).
       - RPO = 0: the previously-committed record (dr-test-node-1) was present, unchanged, on the
         new leader immediately after failover.
       - The surviving 2-node majority kept serving BOTH reads and writes throughout the
         partition: a second command (`JOIN|dr-test-node-2|`) was proposed to and committed by
         the new leader while node-A remained fully disconnected, and replicated correctly to the
         other surviving follower.
  6. THE HEAL: `docker network connect dr-net node-A` -- reconnected the real network partition.
       - Measured convergence time (heal to node-A's /state matching the rest of the cluster):
         ~374ms. node-A caught up via real raft log replication/catch-up over the network, no
         manual intervention.
       - Final state identical and independently verified on ALL THREE containers:
         {"chain_ok":true,"log_len":2,"nodes":{"dr-test-node-1":"UP","dr-test-node-2":"UP"}} --
         confirmed via direct HTTP calls to each container's own /state endpoint, not inferred.

What this does NOT close (honest boundary):
  - three containers on one Docker bridge network on one host, not genuinely separate
    datacenters/cloud regions -- this proves the CONSENSUS/FAILOVER MECHANISM survives a real
    network-level partition between independent processes, not real cross-region network
    characteristics (WAN latency, asymmetric partitions, regional cloud provider outages)
  - the "region" abstraction itself (pkg/blockers/dr.RegionProvider) was not used here; this
    drill exercises the underlying raft/transport primitives it is built on (raftlite +
    rafttcp + distributed.Registry) directly and more concretely, via the actual shipped binary
    rather than the qualification harness's own RegionProvider interface
  - only 2 of 3 nodes ever went down at once (single-node partition, not a full-region failure of
    multiple nodes simultaneously) -- a stronger drill would partition an entire simulated
    "region" of 2+ nodes at once against a larger cluster
  - no cross-region data residency, compliance, or DNS/traffic-manager cutover concerns were
    exercised -- this is a consensus/availability drill, not a full operational DR runbook
    rehearsal (see docs/runbooks/multi-region-dr.md for the procedural side, still unrehearsed
    against real infrastructure)

verdict: the specific mechanism multi_region_dr's acceptance criteria ask for --

  post-heal convergence across three genuinely separate containers. The remaining gap is squarely
  "real cross-datacenter infrastructure" (WAN characteristics, real cloud regions, real
  traffic-manager cutover), not "the failover mechanism is unproven". All binaries, images,
  containers, and CA material were built/run from scratch space and removed after capturing this
  evidence; nothing from this drill was committed to the repository.
