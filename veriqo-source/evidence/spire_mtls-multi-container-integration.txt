Extends evidence/spire_mtls-local-integration.txt (single node, one server, one agent, same

file's explicitly listed gaps:

  1. Built two `FROM scratch` Docker images locally (no golang/alpine pull needed -- the SPIRE
     release binaries are themselves statically linked, `not a dynamic executable` per `ldd`):
     spire-server:local (spire-server binary + server.conf, bind_address 0.0.0.0:8081) and
     spire-agent:local (spire-agent binary + agent.conf, server_address "spire-server", the
     Docker-network DNS name -- not localhost).
  2. Created a real Docker bridge network (`spire-net`) and started THREE separate containers on
     it: spire-server, agent-1, agent-2. Docker's embedded DNS resolved "spire-server" from inside
     the agent containers to its real bridge IP (172.18.0.2); agents got 172.18.0.3 and 172.18.0.4
     -- three independent network namespaces, not three goroutines in one process.
  3. Generated two DISTINCT real join tokens from the real server
     (29648a45-ddeb-48e9-b4d2-15bc883f3549 for agent-1, 9ee51652-5d59-457f-8b67-2ebef57ece4b for
     agent-2) and used each to attest a SEPARATE agent container over the real TCP network
     connection (not a Unix socket in a shared filesystem). Both attestations succeeded
     independently: `spire-server agent list` shows 2 distinct attested agents afterward, each
     with its own SPIFFE ID, expiration and serial number.
  4. Registered one workload entry parented to each agent's own node SPIFFE ID
     (spiffe://veriqo.multicontainer-test/workload/service-on-agent-{1,2}) and fetched a real
     X.509-SVID from EACH agent's own Workload API socket via `docker exec agent-N spire-agent api
     fetch x509` -- each agent returned only its own entry's SVID (node-scoped workload isolation
     confirmed: agent-1 never saw agent-2's identity or vice versa), both chaining to the SAME
     server CA (CA #1 validity window identical across both fetches).
  5. Revocation, now checked ACROSS the live multi-container cluster rather than within one
     process: deleted agent-1's workload entry via `spire-server entry delete`, then re-fetched
     from BOTH agents.
       - Immediately after deletion, agent-1 still returned its (locally cached) SVID -- the
         Workload API serves from the agent's local sync cache, not a live per-call round trip;

       - After the cache resync interval elapsed (~8s), agent-1's fetch failed with the real gRPC

       - agent-2, whose entry was never touched, kept returning its valid SVID unaffected
         throughout -- proving revocation is isolated per-node in a genuine multi-agent
         deployment, not just per-process as the single-node round could show.
