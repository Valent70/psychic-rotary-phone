What this surfaced (a real integration finding, not assumed): the FIRST attempt, using the
existing multi-container round's trust_domain ("veriqo.multicontainer-test"), FAILED with
`rafttcp: expected peer identity "spiffe://veriqo.global/node/node-a", got
"spiffe://veriqo.multicontainer-test/node/node-a"`. pkg/transport/rafttcp's client-side identity
check (rafttcp.go, getConn) hard-codes the expected trust domain as "veriqo.global" when building
the SPIFFE ID it compares the server's presented certificate against -- a real constraint this
live drill discovered that no synthetic-cert test could, since every synthetic test mints its own
self-consistent trust domain. This drill's SPIRE server was reconfigured to trust_domain =
"veriqo.global" to match, and the handshake then succeeded. A real production deployment against
an organization's own SPIRE server (whose trust domain is very unlikely to literally be
"veriqo.global") will hit the identical error unless either (a) the org's trust domain is set to
"veriqo.global", or (b) rafttcp's hard-coded trust domain is made configurable -- real, scoped,
un-started follow-on engineering, now precisely named instead of theoretical.
